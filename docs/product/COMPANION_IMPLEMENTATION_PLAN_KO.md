## 2. 이번 변경과 안전한 기본값

- 기존 나무/집중 CTA·체크인 아래 카드 하나. 제공 가능한 대표 한 개만 표시한다. 가짜 대안/카탈로그/잠금 상품을 만들지 않는다.
- 개발 flavor에서만 카드·세션·기록 경로 허용. 운영 flavor는 직접 경로도 차단. 텍스트 샘플이며 영상·음성은 제공되지 않는다고 준비 화면에 표시한다.
- ‘책상에 시작할 자리 만들기’, 약 2분, 준비물과 4개 구체적 행동. 바로 시작하고 설정은 선택 사항이다.
- 텍스트 직접 넘기기가 기본. 선택적 자동 안내는 단계마다 충분히 기다리되, 안내 진행은 행동 증거가 아니다. 정지/이어하기/다시 읽기/다음/중간 결과 확인/나중에 이어하기를 제공한다.
- 화면 이탈·백그라운드·잠금 시 자동 진행을 멈춘다. 재실행은 저장한 단계에서 정지 상태로 복원한다. 배경 타이머나 오디오 제공을 약속하지 않는다.
- 안내 종료와 결과는 별개. `하려던 만큼 했어요 / 조금 시작했어요 / 오늘은 어려웠어요`를 직접 선택해야 기록한다. 중간 종료도 결과를 선택하거나 미확인 상태로 보관한다.
- 결과 선택 전 로컬 실행만 존재한다. 결과는 session ID당 한 번 확정, 재요청은 기존 결과 반환. 저장 실패는 성공으로 표시하지 않고 같은 선택을 재시도할 수 있다.
- 리포트에서 연결되는 별도 ‘생활 행동 기록’ 목록에 자기보고·날짜·샘플을 명시. 집중시간과 성장·7일 집중 시도에는 합산하지 않는다. 삭제는 기존 계정 삭제와 개별 기록 삭제로 제공한다.
- 새 SDK·네트워크·OS 권한·AI 호출 없음. 실제 사람의 동행 가치/재사용/결제 의향을 검증했다고 보고하지 않는다.

## 3. 데이터와 상태 계약

`CompanionContent(id, version, title, preparation, steps)`는 앱에 포함된 버전 고정 텍스트다.
`CompanionRun`에는 안정적 ID, 콘텐츠 ID/버전, 시작 UTC/로컬 날짜, 현재 단계, 안내 완료, 결과 대기 상태를 둔다.
`CompanionOutcomeRecord`는 run ID에 연결된 자기보고 enum·확인 UTC/로컬 날짜다. 안내 종료에서 생성하지 않는다.
사용자 자유 입력·사진·진단·메시지 본문은 받지 않는다. 실행과 결과는 기기 전용이며 서버 serializer를 만들지 않는다.

Drift v4는 기존 테이블을 수정하지 않고 실행/결과 테이블을 추가한다. 활성 실행은 한 개로 제한하고 결과 제출과 활성 해제는 동일 트랜잭션이다.
기존 v2/v3 fixture를 v4로 올려 기존 집중·나무·체크인 보존, 빈 생활 기록, 제약 유지 및 삭제를 검증한다. 기존 v1 테스트도 유지한다.
기록을 다시 여는 동안 콘텐츠 버전이 없어지면 새 버전으로 조용히 대체하지 않는다. 오류 안내와 안전한 홈 이동을 제공하며 버전 보존을 출시 게이트로 둔다.

상태: 준비 → 안내(메모리의 재생/정지, 단계는 DB) → 결과 대기 → 결과 저장.
화면 이탈 → 단계 보존/정지. 다시 진입 → 재생 자동 시작 없음. 결과 저장 뒤 다음 콘텐츠 자동 추천 없음.

## 5. 콘텐츠 제작 설계

총 10개(무료 4/확장 후보 6), 목적·준비·3~5단계·마무리와 무료 3개 진행 대본/촬영·자막 타임라인은
[콘텐츠 제작안](COMPANION_CONTENT_KO.md)에 둔다. 제작안은 납품 영상이 아니다.
영상에는 진행자가 함께 행동하는 장면과 긴 무음 구간을 넣고, 친근한 성인 말투·큰 자막·배경 음악 없는 기본판을 만든다.
초상·음원·영상/편집·자막·배포·유료 이용 권리와 만료·철회 대응을 확인한 자료만 공개한다.

## 6. 성장 연결 설계 — 이번에는 실행하지 않음

현 원장은 `sourceSessionId`가 **집중 세션 FK**다. 생활 2분을 가짜 집중으로 넣거나 `CompleteFocusSession`을 호출하면 안 된다.
후속 ADR에서 결과가 `asPlanned/started`인 경우의 하루 1회 성장 자격과 기존 집중 대비 균형을 검토한다. `difficult`·미확인은 지급도 차감도 없다.
기존 원장을 보존하는 공통 원인 테이블 또는 원인별 nullable FK+정확히 하나 제약을 설계하고,
`(treeId, creditedLocalDate)` 전역 unique와 원인 run ID unique를 유지한다. 자기보고 확정/성장 지급은 한 트랜잭션으로 묶는다.
기존 ruleVersion/단계는 유지하며 과거 샘플 결과를 소급 지급하지 않는다. 유료 가속·새 재화·새 나무는 없다.
자정·시간대 변경은 시작 날짜 고정, 집중/생활이 같은 날 완료되거나 동시 재시도해도 전체 하루 한 번이다.

## 7. 무료·유료, 가격 및 권한 설계 — 이번에는 실행하지 않음

무료는 기존 무료 기능, 대표 4개 무제한 반복, 해당 영상/음성/자막, 기록, 중단/복원/접근성/삭제/성장이다.
유료 후보는 실제 확보한 확장 콘텐츠, 짧은 코스, 개인 루틴이며 제공하지 못하는 혜택은 팔지 않는다.
온보딩·어려움 표현에 페이월을 띄우지 않는다. 확장 콘텐츠 직접 선택 시 미리보기와 무료 대체를 제공한다.
서로 다른 날 재사용 후 작은 가치 소개 카드는 선택적으로 검토하고, 닫은 뒤 14일 억제하는 가설을 한 번에 하나씩 검증한다.

현재 `config/apple-identifiers.json`과 이전 Scope Freeze에는 월 5,900원/연 39,000원/7일 체험이 있지만 실제 결제 구현은 없다.
사용자 요청의 월 4,900원/연 34,900원은 새 **검증 가설**이고 연간·자동전환 체험은 초기 비활성이다. 기존 설정 파일과 실제 상품을 이번에 변경하지 않는다.
후속 작업에서 실판매 상품·기존 구독자의 계약을 확인하고 가격 계약 버전을 확정한다. 동일 Dopa Plus 혜택의 중복 구독은 만들지 않는다.

연동 후보: Flutter용 RevenueCat을 StoreKit/Google Play Billing 앞의 구매·복원 어댑터로 검토한다. SDK 설치는 보류한다.
신뢰 계층의 검증된 entitlement, 만료 시각, 플랫폼/환경을 기준으로 접근하며 클라이언트 성공 콜백만으로 권한을 부여하지 않는다.
서버의 인증된 webhook/재조회는 event ID로 멱등 처리하고 순서 역전은 최신 권한 재조회로 해결한다.
상태별 계약: 취소/실패/보류는 새 권한 없음; 검증된 구매/복원은 남은 권한; 해지 예약은 만료 전 유지;
만료/환불·철회는 신뢰 상태에 따라 차단; 결제 유예는 검증된 만료/유예 정책에 한정. 네트워크/상품 조회 실패는 구매 비활성·재시도·무료 대체.
기존 가입자의 유효 권한은 복원 후 유지한다. 개발 bypass는 운영 빌드에서 불가해야 한다.
가격은 스토어의 현지 금액/주기, 자동갱신 여부, 현재 혜택, 관리/복원, 약관/개인정보 링크를 실제 조회값으로 표시한다.
거짓 할인/카운트다운/이용자 수/체험은 금지한다. 국가별 외부 결제 예외를 추정 적용하지 않는다.
유료 미디어는 서버 권한 확인 후 만료 URL, 콘텐츠 버전 기반 캐시, 만료/철회 재검증 및 로그아웃 캐시 삭제를 함께 설계한다.
SDK·스토어 정책은 결제 착수 시 최신 공식 문서와 실제 계정 설정을 다시 검증해야 한다.

설계 근거(2026-09-10 공식 문서 확인): RevenueCat은 Flutter에서 현재 entitlement를 조회하고 구매를 복원하는 경계를 제공한다.
[CustomerInfo](https://www.revenuecat.com/docs/customers/customer-info), [구매 복원](https://www.revenuecat.com/docs/getting-started/restoring-purchases).
이를 후보로 택한 것은 두 모바일 플랫폼의 구독 검증/복원 운영을 한 경계로 관리하기 위한 설계 판단이며 실제 도입·연동은 아니다.
Apple은 자동갱신 구독에 지속 가치를 요구한다. 고정된 콘텐츠 열 개만으로 충분하다고 판단하지 않는 근거다.
[App Review 3.1.2](https://developer.apple.com/app-store/review/guidelines/).
Google Play의 최신 상태는 서버 조회로 확인하고 유예/보류/해지/만료를 구분해야 한다.
[구독 수명주기](https://developer.android.com/google/play/billing/lifecycle/subscriptions).

## 8. 분석과 실험 설계 — 전송은 이번 범위 밖

현재 분석 SDK/동의 설정이 없어 이벤트를 임의 전송하거나 로컬 개인 기록을 분석 outbox로 바꾸지 않는다.
후속 `analytics_contract`는 선택적 동의 이후 typed allowlist, 익명·회전형 분석 식별자, test/dev/sandbox 제외 및 철회/삭제를 함께 구현한다.

| 이벤트 | 발생 조건 / 중복 키 |
|---|---|
| companion_entry_viewed | 카드가 실제 보인 노출, 화면 방문 내 1회 |
| companion_session_started | 실행 생성 성공, 실행당 1회 |
| companion_session_interrupted | 배경/사용자 중단, 중단 전이당 1회 |
| companion_guide_ended | 안내 끝, 행동 성공과 별개 |
| companion_session_outcome_submitted | DB에서 처음 결과 확정. 3개 enum 구분, 실행당 1회 |
| premium_offer_viewed / paywall_viewed | 사용자가 실제 본 제안/페이월, 노출 ID당 1회 |
| purchase_started / purchase_verified | 요청/신뢰 검증 성공 분리, 검증 transaction당 1회 |
| subscription_renewed / subscription_expired_or_revoked | 신뢰 서버 이벤트, event ID당 1회 |

공통 속성: content ID/version, home/focusCompletion 진입 경로, 플랫폼, 앱 버전, free/paid, 실험군, dev/test/prod와 sandbox 구분.
실행 ID는 로컬 멱등성 키이며 원본 집중/나무 ID·정확한 날짜를 외부 이벤트에 복제하지 않는다. 코호트/날짜 집계 설계는 개인정보 검토 후 확정한다.
자유 입력/진단/메시지/인증 토큰/영수증 본문은 전송 금지. 분석 거부도 무료 기능·기록·삭제에 영향 없어야 한다.

핵심은 **정해진 현지 달력 주에 서로 다른 2일 이상 asPlanned 또는 started로 확인한 실제 사용자 수**다. 이는 자기보고이며 객관적 생활 개선 측정이 아니다.
첫 실험은 같은 모집일군 성인 30명에게 14일 기회를 제공한다. 신규와 기존 사용자를 별도 코호트로 보고한다.
진입→시작 비율의 분모는 해당 기간 실제 진입 노출 사용자, 시작→확인의 분모는 시작 사용자,
다른 날 재사용의 분모는 첫 확인 사용자(모두 동일 14일 관찰을 마친 cohort)다. 전체 30명 중 서로 다른 3일 이상 사용 10명을 임시 다음 투자 기준으로 둔다.
유료 제안→구매 분모는 제안을 본 적격 실제 사용자, 갱신 분모는 다음 결제일과 유예 종료 관찰까지 도달한 실제 월 결제자다.
정상 판매 단계의 3명 결제, 다음 기회 도달자 중 2명 갱신은 임시 내부 기준이며 업계 기준/통계적 확정이 아니다. 실제 n/N와 기간을 함께 보고한다.
샘플·개발자·테스터·sandbox는 실사용/매출에서 제외한다. 영상 호감과 실제 반복 사용을 구분한다.
반복이 약하면 콘텐츠/경험, 반복이 강하고 결제가 약하면 유료 가치 차이, 갱신이 약하면 지속 가치/기대 불일치를 먼저 검토한다.

## 9. 수익성 검토 입력표와 운영

기간별 월/연 실결제액·실결제자·환불·실제 정산액을 각각 입력한다. 확인 전 값은 공란이며 확정 수수료율을 만들지 않는다.
정산액에는 이미 반영된 수수료/세금을 중복 차감하지 않는다. 연간 현금 수입 전액을 월 반복매출로 쓰지 않으며, 필요 시 계약 기간에 걸친 월 배분과 현금 지표를 나눠 표시한다.
기간 손익 = 실제 정산 수입 − (전체 무료+유료 미디어 전송/저장 + 서버 + 콘텐츠 제작/편집/출연 + 고객 지원 + 운영 시간×시간 단가 + 고객 확보 비용).
모든 단가·시간·재생량은 변경 가능한 관측 입력이고 무료 사용자 비용도 포함한다. 갱신 cohort와 유료 유지율을 비용표 옆에서 평가한다.
초기 10개 이후 월 1개 제작을 운영 가설로 두되 실제 제작시간/출연료/지원비를 먼저 기록한다. 지속 운영이 감당되지 않거나 반복 가치가 약하면 같은 콘텐츠의 일회 묶음 판매를 **대안 실험**으로 검토한다. 여러 과금 모델을 동시에 구현하지 않는다.
